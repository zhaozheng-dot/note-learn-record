## 学习目标

- 搞懂 dsh 插件"装了之后 agent 为何知道它存在、又为何知道在什么场景调用"——从"会用"到"懂原理"。
- 用 describe-image 这一真实插件验证通用机理，沉淀成知识笔记（带实例）。

## 学习过程

### 第一次学习（2026-08-16）

**学习内容：**
- 插件的五阶段机理：装载（bundles/cordis.patch insert）→ 注册（apply(ctx) + ctx.tools.register(defineTool)）→ 暴露（tool schema 注入会话系统提示）→ 触发（description 文案 + 模型语义匹配）→ 配置分层（settings.yaml → 凭据服务 → 环境变量）。
- 四层认知框架：①工具注册（存在性，硬机制）②描述自述（场景锚定）③触发决策（模型判断，概率性）④跨会话记忆（增强，非必需）。

**关键理解：**
- "存在"和"何时用"是两回事：存在靠代码保证（注册进工具清单），何时用靠 description 文案 + 语义匹配，没有硬保证。
- 跨会话记忆不是触发插件的原因，只是增强——新会话里工具照样在工具表里。

**实践验证：**
- 亲手把 describe-image 的 404（baseURL 缺 /v1）修好，端到端调通本地图片 + 真实图片 URL + 粘贴图片（IMG_1787.JPG OCR 正确）。
- 把密钥从 settings 明文迁到 `apiKeyEnv: VISION_API_KEY`（凭据服务），验证配置分层生效、免重启即时生效。
- 确认 plugin `fetch(url, {redirect:'error'})` 拒绝重定向——这解释了"为何 OSS 图床必须公开读/无重定向固定 URL"。

**疑问：**
- 无（本主题机理已闭环）。
